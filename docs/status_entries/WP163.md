## Schema, bounds, and configuration

- Exactly two application tables (`record_store_meta`, `records`) and five
  explicit indexes on ingestion/observed/event time and market/source id.
- DELETE journal, FULL synchronous writes, enabled foreign keys, `timeout=0.0`,
  and explicit `BEGIN IMMEDIATE`; read URI mode `ro`, existing-write `rw`,
  creation `rwc`.
- Bounds: 256 records per append, 4096 records per store, 131072 canonical
  full-record payload bytes per row, and 134217728 total canonical payload bytes.
- The complete immutable record object (envelope plus every record field) is
  persisted as canonical JSON with a SHA-256 digest; indexed columns are the exact
  projection of the reconstructed object.

## Ordinary and review-conflict integrity

- An ordinary record self-validates through `validate_record_batch` with its own
  lineage parents as known external parents and must reproduce exactly its
  committed record-version id.
- A CONFLICT record self-validates through `revalidate_review_conflict_record`,
  is always human-review-required, and never becomes an ordinary authority.
- Complete cross-record lineage is validated on append and on load: parent
  existence, no duplicate/self parent, no cycle, supersedes resolves to a
  non-CONFLICT lineage parent, correction identity/time rules, and exact/semantic
  duplicate comparison against a non-CONFLICT reference parent.

## Materialization modes

- A caller `DatasetSnapshotReference` is rebuilt through the public
  `build_dataset_snapshot_reference` and must equal the caller before any store
  access; the fully verified store then resolves every ordinary and review id in
  exact reference-owned order with exact authority classification.
- `VALIDATED_RECORD_BATCH` recomputes `validate_record_batch` over the resolved
  ordinary records and proves the accepted ids and `canonical_batch_sha256` match
  the reference (`VALIDATED_BATCH_RECOMPUTED`).
- `AS_OF_QUERY_RESULT` is honestly id-resolution only
  (`AS_OF_REFERENCE_IDS_RESOLVED`): it never recomputes the query spec/result or
  batch hash from the output subset and never claims a full WP157 query replay.
