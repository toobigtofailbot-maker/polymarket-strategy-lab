## Locked mapping semantics

- Batch adapter re-runs `validate_record_batch`, refuses an empty valid batch,
  and uses `derivation_mode=VALIDATED_RECORD_BATCH`,
  `validated_batch_sha256=canonical_batch_sha256`, and ordinary IDs equal to the
  accepted record-version IDs; the six query fields are null.
- As-of adapter re-runs `query_point_in_time_record_set` and maps ordinary IDs by
  result view: `AUTHORITATIVE_CURRENT_STATE` uses the authoritative IDs,
  `VISIBLE_HISTORY` and `ENTITY_TIMELINE` use the history IDs; review-conflict IDs
  stay separate and set `human_review_required`.
- Explicit provenance rule: every input record's envelope `parameter_set_id` and
  `validator_version` must match the caller/receipt values; mixed values reject.
- The reference identity is recomputed from the exact WP158/WP160 preimage and
  rebuilt through the public builder; the REGISTER entry identity is recomputed
  from the exact WP160 preimage and rebuilt through the public builder.
- The store must already exist and verify; the adapter never creates, repairs, or
  migrates a store, never generates wall-clock time, and never accepts a
  caller-supplied sequence number or previous-entry ID.
- Manifest ID: genesis adopts the caller ID; an existing chain must match exactly.
- Sequence/previous head are derived from the verified snapshot; the REGISTER
  entry is appended through the WP161 public API only.
- Exact retry of an already-registered identical snapshot is idempotent
  (`ADAPTER_ALREADY_PERSISTED`), remains idempotent after the chain advances, and
  a changed `effective_time` is a registration conflict.
