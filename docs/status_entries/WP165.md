## Cumulative lineage, baseline convergence, and capacity

- Every cross-run parent is a record already committed in the same WP163 store; the
  prior registered records plus the new lineage records are validated together with
  no external known parents and registered as one WP160 `DatasetSnapshotReference`.
  `WP162-D004` stays OPEN; no schema migration and no external known-parent context
  is introduced. The cumulative total is bounded to 256 records.
- Before any network the latest registered `VALIDATED_RECORD_BATCH` reference is
  proven to converge exactly with the registered store portion by set equality, a
  re-run `validate_record_batch` whose accepted ids and batch hash match the
  reference, and a `VALIDATED_BATCH_RECOMPUTED` materialization. A strict superset
  store yields `INCREMENTAL_BASELINE_UNREGISTERED` with `recovery_required=True`.
- Worst-case capacity `existing + bounded markets + bounded books` is checked before
  any client call; over 256 rejects with `INCREMENTAL_CAPACITY_EXCEEDED`.
- New captures are classified `PRIMARY_ASSERTION` / `EXACT_DUPLICATE` /
  `SOURCE_REVISION` against the latest prior for the WP156 entity; identity drift
  rejects with `INCREMENTAL_IDENTITY_DRIFT`.
- Only new records are appended (records first), then the complete cumulative
  dataset is registered (reference second). A post-append registration failure
  returns `INCREMENTAL_RECORDS_PERSISTED_REGISTRATION_FAILED` with
  `recovery_required=True` and never deletes records.

## Offline recovery behavior

`recover_incremental_polymarket_public_registration` performs zero network activity,
constructs no client, and never writes records. It is a valid
`INCREMENTAL_ALREADY_REGISTERED` no-op when the store already converges; otherwise it
re-registers exactly one genuine WP165 orphan run (1..45 records reconstructed
object-for-object from the registered prior state, with the run identity recomputed
from the orphan payload hashes) through WP162. A forged, multi-batch, drifted, or
mismatched orphan set fails closed as `INCREMENTAL_RECOVERY_INVALID`.
