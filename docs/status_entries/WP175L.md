## What WP175L Fixes

WP175L replaces the conceptual `_minimal_env()` with a deterministic platform-aware
HYBRID SANITIZED RUNTIME ENVELOPE (`_build_sanitized_runtime_env`) — an explicit
allowlist, never `os.environ.copy()` and never a denylist-only model.

Side11's exact-head review of `c73934c` raised BLOCKING **Finding E**: forwarding the
REAL per-user `LOCALAPPDATA`/`USERPROFILE` let pinned
`hermes_cli/main.py::_apply_profile_override` (which trusts an explicit `HERMES_HOME`
immediately only when its immediate parent directory is literally `profiles`, and
otherwise computes `get_default_hermes_root()` and reads `<default root>\active_profile`)
read a sticky personal `%LOCALAPPDATA%\hermes\active_profile` and re-home the explicit H1
`HERMES_HOME`. Our canonical H1 home is a ROOT-style directory, not `...\profiles\<name>`,
so correctness must not depend on unrelated personal Hermes state.

The hybrid envelope therefore distinguishes machine context (safe to inherit) from
per-user identity roots (must be controlled):

- **Real MACHINE/runtime values forwarded from the parent:** `COMSPEC`, `PATHEXT`,
  `WINDIR`, `OS`, `PROCESSOR_ARCHITECTURE`, `NUMBER_OF_PROCESSORS`, `PROGRAMDATA`,
  `PROGRAMFILES`, `PROGRAMFILES(X86)`, `COMMONPROGRAMFILES` (plus the cross-platform
  neutral set `PATH`, `SystemRoot`, `TEMP`, `TMP`, `TMPDIR`, `LANG`, `LC_ALL`).
- **Per-user Windows identity roots SYNTHESIZED, never inherited:** `USERPROFILE`,
  `HOMEDRIVE`, `HOMEPATH`, `LOCALAPPDATA`, `APPDATA` are derived from a backend-owned
  ephemeral runtime-user root (`<runtime-root>\winuser`, with `AppData\Local` and
  `AppData\Roaming` created before launch), so `Path.home()` works, the pinned default
  root resolves under a controlled `LOCALAPPDATA` (`<synthetic LocalAppData>\hermes`) that
  carries no unrelated `active_profile`, and the explicit H1 `HERMES_HOME` stays
  authoritative. The synthetic roots live under the existing ephemeral cwd / probe home
  and disappear under the existing teardown on success, nonzero exit, timeout, and launch
  failure.

The secret-name rejection (`KEY`, `SECRET`, `TOKEN`, `PASSWORD`, `CREDENTIAL`, `AUTH`,
`PRIVATE`) is retained, and an explicit control / interpreter / shell / capability
injection denylist is added (`PYTHONPATH`, `PYTHONHOME`, `PYTHONSTARTUP`, `PYTHONINSPECT`,
`NODE_OPTIONS`, `BASH_ENV`, `ENV`, `SSH_AUTH_SOCK`, `GIT_ASKPASS`, `GIT_SSH_COMMAND`,
`KUBECONFIG`, `GOOGLE_APPLICATION_CREDENTIALS`, `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`,
`NO_PROXY`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, and the `AWS_` / `AZURE_` / `DOCKER_` /
`DYLD_` / `PYTHON` prefixes). The inherited allowlist is disjoint from the secret-name,
injection, per-user, and control-plane boundaries; no ambient provider credential reaches
the child. Provider credentials for H1 continue to come only from Hermes' own loading of
the explicit H1 home.

WP175L also adds a second OFFLINE startup/profile-init preflight. `hermes --version` is
answered by the pinned fast-version path
(`hermes_cli/_startup_fast.try_fast_version()`) before profile initialization, which is why
version preflight passed while H1 #2 failed in `_apply_profile_override()`. The new
preflight runs `hermes --help` — which the pinned tagged CLI resolves through
`_apply_profile_override()` -> `get_default_hermes_root()` before argparse prints help and
exits, and unlike `--version` does not use the fast-version path — through the same
sanitized runtime envelope and a throwaway `HERMES_HOME` with the update check disabled.
It forwards no provider secret, makes no research/provider/Firecrawl/network call, is
bounded by a short timeout, discards its output, and always removes its temporary home.
