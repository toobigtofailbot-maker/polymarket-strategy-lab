# Append-Only Local Manifest And Deterministic Dataset Snapshot Reference Contract

## 1. Contract Label And Posture

- Contract label:
  `APPEND_ONLY_LOCAL_MANIFEST_AND_DETERMINISTIC_DATASET_SNAPSHOT_REFERENCE_CONTRACT`
- Contract posture:
  `CONTRACT_ONLY_NO_WRITER_NO_READER_NO_PERSISTENCE`
- Package class: contract-first / documentation / tests / repo-truth only.
- Capital at risk: USD 0.

This document is a contract package only. It defines the immutable logical shape,
identity preimages, append-chain invariants, validation/error semantics, and
non-authority boundaries for a future local append-only manifest and a
deterministic dataset snapshot reference. It implements no Python runtime
surface.

WP158 does not implement a writer, reader, filesystem persistence, JSONL/SQLite,
Arrow/Parquet, DuckDB/Polars, file locking, atomic append, crash recovery,
migrations, collectors, network calls, credentials, schedulers, strategy,
paper/live trading, or execution. It adds no new `src` file, no new package-root
export, no dependency, no lock file, no workflow, and no local or generated data
artifact.

## 3. Objective And Scope Boundary

Define and lock a contract for:

- an immutable deterministic `DatasetSnapshotReference`;
- an append-only local `ManifestEntry`;
- deterministic identity / hash preimages;
- append-chain and sequence invariants;
- provenance links to merged WP156 record identity and WP157 query identity;
- bounded validation / error semantics for a future implementation;
- explicit non-authority and storage boundaries.

References, not copies: a dataset snapshot reference commits only logical
identities and hashes of already-valid upstream artifacts. It never copies raw
payload, source text, question/rule text, prices/sizes, order-book content,
wallet/account/credential identifiers, strategy/signal/trade fields, or any
runtime/environment value.

Append-only: the manifest is a single linear hash-linked chain. There is no
in-place mutation, no deletion, no branching, no multiple heads, and no
implicit latest-by-time resolution.

Local / advisory: every reference and every manifest entry fixes
`advisory_only=true` and `no_execution_authority=true`. This contract grants no
runtime or trading authority.

## 4. Locked Architecture Decisions

- Contract-only: no Python runtime implementation and no new package export.
- Logical identity only: no storage container or storage technology is selected.
- References, not copies: no payload / source / rule / question / order-book
  content is ever embedded.
- Append-only: no in-place mutation and no deletion.
- Local / advisory: fixed `advisory_only=true` and
  `no_execution_authority=true`.
- Review conflicts remain separate and never authoritative.
- No wall-clock value is generated by identity or by the chain.
- Dataset visibility inherits WP157 ingestion-time semantics; this contract
  introduces no new visibility rule and no look-ahead.

### 6.1 Required Logical Fields

1. `schema_id`
2. `schema_version`
3. `dataset_snapshot_reference_id`
4. `derivation_mode`
5. `validated_batch_sha256`

10. `cutoff_mode`
11. `cutoff_time`
12. `result_view`
13. `query_engine_version`
14. `validator_version`
15. `parameter_set_id`
16. `created_from_manifest_entry_id`
17. `human_review_required`
18. `advisory_only`
19. `no_execution_authority`

### 6.2 Rules

- `schema_id` and `schema_version` are exact constants
  (`point-in-time-dataset-snapshot-reference` and `1.0.0`).
- `dataset_snapshot_reference_id` is derived from the canonical preimage and is
  never trusted from caller input.
- `validated_batch_sha256` is always required.
- The record-version ID tuples are immutable and ordered. A duplicate ID within a
  single tuple, or a malformed tuple member, is rejected with
  `FIELD_VALUE_INVALID`. The two tuples MUST NOT overlap; any ID appearing in both
  `ordinary_record_version_ids` and `review_conflict_record_version_ids` is
  rejected with `REVIEW_CONFLICT_AUTHORITY_FORBIDDEN` (a review-conflict ID may
  never gain ordinary / authoritative status). Cross-authority overlap takes
  precedence over the generic within-tuple duplicate rule.
- `ordinary_record_version_ids` may be empty only for an empty or review-only
  valid as-of result.
- `review_conflict_record_version_ids` never become authoritative.
- For `VALIDATED_RECORD_BATCH`, all query fields (`query_spec_sha256`,
  `query_result_sha256`, `cutoff_mode`, `cutoff_time`, `result_view`,
  `query_engine_version`) are null.
- For `AS_OF_QUERY_RESULT`, all query fields are required.
- `created_from_manifest_entry_id` is a reserved field in schema version
  `1.0.0`: it MUST be present and MUST be null. It is never populated after
  registration and is excluded from reference identity to avoid circularity.
  Registration provenance is one-way — a `ManifestEntry` points to its
  `DatasetSnapshotReference` through `dataset_snapshot_reference_id`, never the
  reverse. A future reader may derive the reverse lookup by scanning or indexing
  manifest entries, but no backlink is ever stored by mutating the reference. Any
  future non-null backlink requires a new schema version and a separately
  approved migration / identity decision. A non-null
  `created_from_manifest_entry_id` under schema `1.0.0` is rejected with
  `FIELD_VALUE_INVALID`.
- `human_review_required` is `true` when `review_conflict_record_version_ids` is
  non-empty.
- `advisory_only` and `no_execution_authority` are fixed `true`.

### 6.3 Forbidden Fields

A dataset snapshot reference never contains: raw payload, source text,
question/rule text, prices/sizes, wallet/account/credential identifiers,
strategy/signal/trade fields, filesystem path, hostname, process ID, runtime
duration, current time, and object representation (`repr`/`str` of source
objects).

### 6.4 Reference Immutability Invariant

The full canonical `DatasetSnapshotReference` content is immutable after
`dataset_snapshot_reference_id` is derived. No field may change under the same
ID — including a field that is excluded from the identity preimage, such as
`created_from_manifest_entry_id`. Because `created_from_manifest_entry_id` is
fixed null in `1.0.0`, one `dataset_snapshot_reference_id` always identifies
exactly one canonical content; there is no before-registration versus
after-registration divergence, and no excluded mutable field may create a
same-ID / different-content ambiguity.

## 7. Dataset Snapshot Reference Identity

```
dataset_snapshot_reference_id = "datasetref:sha256:" + SHA-256(canonical_preimage)
```

### 7.1 Exact Preimage Mapping

The identity preimage is a JSON object with exactly these keys (and no others):

```text
{
  "schema_id": ...,
  "schema_version": ...,
  "derivation_mode": ...,
  "validated_batch_sha256": ...,
  "ordinary_record_version_ids": [...],
  "review_conflict_record_version_ids": [...],
  "query_spec_sha256": ...,
  "query_result_sha256": ...,
  "cutoff_mode": ...,
  "cutoff_time": ...,
  "result_view": ...,
  "query_engine_version": ...,
  "validator_version": ...,
  "parameter_set_id": ...,
  "human_review_required": ...,
  "advisory_only": true,
  "no_execution_authority": true
}
```

Each value is copied verbatim from the reference object. The mapping keys above
are the logical preimage; canonical serialization sorts the keys lexicographically
(Section 7.3), so conceptual field order, JSON key order, and serialization order
are unambiguous and never conflict. Record-version ID arrays retain their given
order.

### 7.2 Excluded From Identity

- the self ID (`dataset_snapshot_reference_id`);
- `created_from_manifest_entry_id`;
- storage metadata;
- all runtime / environment values.

### 7.3 Canonicalization And Derivation

Canonical bytes are produced by a repository-compatible canonical JSON
serialization:

- UTF-8 encoding;
- JSON object keys lexicographically sorted (`sort_keys=True`);
- separators exactly `(",", ":")` — no whitespace;
- explicit nulls preserved;
- array/sequence order preserved;
- `ensure_ascii=False`;
- `allow_nan=False` — no NaN or Infinity, and no floats appear in the preimage.

Derivation:

```text
dataset_snapshot_reference_id =
    "datasetref:sha256:" + sha256(canonical_json_bytes(preimage_mapping)).hexdigest()
```

The digest is a 64-character lowercase hexadecimal string. One-field hash
sensitivity holds: changing any single identity-committed field changes the
reference ID.

14. `human_review_required`
15. `advisory_only`
16. `no_execution_authority`

### 8.2 Structural Rules

- `schema_id` and `schema_version` are exact constants
  (`point-in-time-local-manifest-entry` and `1.0.0`).
- `manifest_id` is a bounded opaque logical ID.
- `sequence_number` is a non-negative integer; a boolean is invalid.
- `sequence_number` 0 requires `previous_manifest_entry_id` null.
- `sequence_number` greater than 0 requires the exact prior entry ID (the
  immediately preceding sequence number's entry in the same chain).
- One `manifest_id` per chain; entries from another manifest are rejected.
- `sequence_number` values and `manifest_entry_id` values are unique.
- Append order is sequence / link based, never effective-time based.
- `effective_time` cannot rewrite prior entries.
- `advisory_only` and `no_execution_authority` are fixed `true`.

### 8.3 Entry-Kind Subject And Target Semantics

The manifest entry's `dataset_snapshot_reference_id` is always the entry's
**subject reference**. What the entry does with that subject depends on the kind.

**`REGISTER_DATASET_SNAPSHOT_REFERENCE`** — registers a new subject reference.

- `dataset_snapshot_reference_id` is the newly registered subject reference.
- `supersedes_manifest_entry_id` MUST be null.
- `reference_state` = `ACTIVE_REFERENCE`.
- `reason_code` = `INITIAL_REGISTRATION`.

**`SUPERSEDE_DATASET_SNAPSHOT_REFERENCE`** — a state-transition record for an
already-registered subject, not a replacement-registration record.

- `supersedes_manifest_entry_id` MUST identify an earlier same-chain
  `REGISTER_DATASET_SNAPSHOT_REFERENCE` (or other currently-effective entry) for
  the same subject.
- `dataset_snapshot_reference_id` MUST equal the target entry's
  `dataset_snapshot_reference_id`.
- `reference_state` = `SUPERSEDED_REFERENCE`.
- `reason_code` = `SOURCE_SUPERSEDED`.
- A replacement reference, when one exists, MUST be registered separately with
  its own `REGISTER_DATASET_SNAPSHOT_REFERENCE` entry; this contract neither
  infers nor requires a replacement.

**`INVALIDATE_DATASET_SNAPSHOT_REFERENCE`** — a state-transition record for an
already-registered subject.

- `supersedes_manifest_entry_id` MUST identify an earlier same-chain
  currently-effective entry for the same subject.
- `dataset_snapshot_reference_id` MUST equal the target entry's
  `dataset_snapshot_reference_id`.
- `reference_state` = `INVALIDATED_REFERENCE`.
- `reason_code` = `REFERENCE_INVALIDATED`.
- `human_review_required` = `true`.

### 8.4 State-Transition Integrity

- A `SUPERSEDE`/`INVALIDATE` target MUST be currently effective. A target that
  is already terminally `SUPERSEDED_REFERENCE` or `INVALIDATED_REFERENCE` is
  rejected; schema version `1.0.0` defines no repeated terminal transition.
- A target that is from another manifest, a future entry, the entry itself
  (self-target), unknown, or whose `dataset_snapshot_reference_id` does not equal
  the transition entry's `dataset_snapshot_reference_id` is rejected.
- The append-chain head and the subject-reference state are separate concepts.
  The highest-sequence entry is the chain head, but it is not automatically the
  active dataset reference; a subject's effective state is determined by the last
  `REGISTER`/`SUPERSEDE`/`INVALIDATE` entry naming that subject.

## 10. Append-Chain Truth Table

In the table, "same subject" means the transition entry's
`dataset_snapshot_reference_id` equals the target entry's
`dataset_snapshot_reference_id`.

| Sequence | Previous ID | Entry kind | Supersedes target | Required result |
|---:|---|---|---|---|
| 0 | null | REGISTER | null | valid genesis |
| 0 | non-null | any | any | reject |
| >0 | null | any | any | reject |
| >0 | exact prior | REGISTER | null | valid append |
| >0 | unknown prior | any | any | reject |
| >0 | prior from other manifest | any | any | reject |
| >0 | exact prior | SUPERSEDE | earlier same-chain effective entry, same subject | valid |
| >0 | exact prior | SUPERSEDE | null/unknown/future/self | reject |
| >0 | exact prior | SUPERSEDE | target dataset-reference ID ≠ entry's | reject |
| >0 | exact prior | SUPERSEDE | target already superseded/invalidated | reject |
| >0 | exact prior | INVALIDATE | earlier same-chain effective entry, same subject | valid with review |
| >0 | exact prior | INVALIDATE | null/unknown/future/self | reject |
| >0 | exact prior | INVALIDATE | target dataset-reference ID ≠ entry's | reject |
| >0 | exact prior | INVALIDATE | target already superseded/invalidated | reject |
| duplicate sequence | any | any | any | reject |
| duplicate ID/different content | any | any | any | reject |
| cycle | any | any | any | reject |

The chain explicitly rejects branching, multiple heads, sequence gaps, cycles,
backward mutation, and implicit latest-by-time resolution. The single valid chain
head is the entry with the highest sequence number reachable by exact previous-ID
links from the genesis entry. The chain head is distinct from any subject
reference's effective state: a subject's state is the last `REGISTER`/`SUPERSEDE`/
`INVALIDATE` entry naming that subject, not the chain head.

Failure precedence is deterministic. When more than one condition could apply to
the record-version tuples, an overlap between `ordinary_record_version_ids` and
`review_conflict_record_version_ids` is reported as
`REVIEW_CONFLICT_AUTHORITY_FORBIDDEN`, which takes precedence over the generic
within-tuple `FIELD_VALUE_INVALID` duplicate rule. Example 12 is therefore a
single-fault example whose deterministic category is
`REVIEW_CONFLICT_AUTHORITY_FORBIDDEN`.

Rejected results may never contain raw caller values, payload/source content,
exception text, traceback, local path, or environment data. A rejection returns
only a bounded category code and a bounded neutral message.

## 14. Deterministic Contract Examples

The twelve examples below are concrete, sanitized, machine-readable JSON objects.
Each is a wrapper with `example_id`, `expected_valid`, `expected_error_codes`,
and an `input` object that is a complete `DatasetSnapshotReference` or
`ManifestEntry`. Every SHA-256 value is exactly 64 lowercase hexadecimal
characters. Every **derived self ID is a true digest**: each
`dataset_snapshot_reference_id` and `manifest_entry_id` is the real
`sha256` of that object's exact canonical preimage (Sections 7 and 9), carrying
the locked prefix, and is independently recomputed and compared by the focused
test — no self ID is a decorative placeholder. Synthetic *reference* values that
point at objects outside this example set (record-version IDs, and the subject
reference IDs carried by manifest entries) remain fixed opaque synthetic IDs.
Explicit nulls are present, safety booleans are present and `true`, and every
reference sets `created_from_manifest_entry_id: null` per the schema `1.0.0`
reserved-null rule. The examples are illustrative and non-runtime: none embeds
raw payload, source text, prices, real market/wallet/account/credential data,
path, hostname, process value, current timestamp, or any generated runtime value.
Each invalid example carries a correctly derived self ID for its content and
fails for exactly one intended bounded category (its stated defect is never
masked by an unrelated ID mismatch).

Wrapper shape:

```text
{
  "example_id": "WP158-EXAMPLE-NN",
  "expected_valid": <bool>,
  "expected_error_codes": [ ... bounded categories, empty when valid ... ],
  "input": { ...complete DatasetSnapshotReference or ManifestEntry... }
}
```

Manifest examples 6–9 form one coherent chain
(`manifest:wp158-synthetic-chain-a`): genesis registers subject A, entry 1
registers subject B, entry 2 supersedes subject A, entry 3 invalidates subject B.

### Example 1 — validated ordinary batch reference (valid)

## 15. Non-Authority And Storage Boundaries

- This contract selects no storage container and no storage technology.
- It authorizes no writer, no reader, no verifier, and no persistence.
- It grants no strategy, signal, paper, order, risk, reconciliation, accounting,
  or execution authority.
- Review conflicts are never authoritative and never promoted by this contract.
- Dataset visibility inherits WP157 ingestion-time semantics unchanged; no new
  look-ahead is introduced.
- WP158 does not implement WP159.

## 16. Deferred Items

WP158 registers deferred items WP158-D001 through WP158-D010 in
`docs/deferred_items_log.md`. Each is `OPEN`, has no implementation authority, and
requires a separately approved work package. The writer, reader/verifier, storage
path/container, atomic append / file locking, crash recovery / torn-write policy,
schema migration, compaction, Arrow/Parquet materialization, DuckDB/Polars query
layer, and signing / external attestation are all deferred.

## 17. Next Separately Gated Package

Suggested next package:

`WP159 — LOCAL OFFLINE STDLIB-ONLY MANIFEST ENTRY AND DATASET SNAPSHOT REFERENCE VALIDATOR WITH SANITIZED SYNTHETIC CORPUS`

WP159 would implement deterministic in-memory validation and building only and
would still exclude filesystem writer/reader, persistence, Arrow/Parquet,
DuckDB/Polars, network, credentials, scheduler, strategy, paper/live, and
execution. WP159 requires separate approval and is not implemented. WP159 is not
implemented in this package.

## 18. Compatibility / Impossibility

A logical append-only manifest and deterministic dataset snapshot reference that
copies no raw content is compatible with WP155/WP156/WP157 without touching
legacy runtime behavior. Persistence, writers, readers, real datasets,
collectors, Arrow/Parquet, DuckDB/Polars, migrations, dependencies, credentials,
scheduling, strategy, paper/live, and execution remain incompatible with the
authorized package and are excluded.

## 19. WP160 Implementation Addendum

This addendum records the functional WP160 realization of the WP158 contract as
a bounded in-memory validation and identity-derivation layer. It does not
rewrite any WP158 historical fact, vocabulary, preimage, truth table, or
example in Sections 1 through 18; those remain authoritative. Where WP160 makes
a more specific implementation decision (for example the fail-closed error-code
precedence below), that decision governs the implementation only.

### 19.1 Implementation Label And Posture

- Implementation label:
  `APPEND_ONLY_LOCAL_MANIFEST_AND_DATASET_SNAPSHOT_REFERENCE_VALIDATION`.
- Implementation posture:
  `BOUNDED_LOCAL_OFFLINE_STDLIB_ONLY_IN_MEMORY_VALIDATION`.
- The layer is import-safe, side-effect-free, deterministic, standard-library
  only, local, offline, and in memory. It has no file, environment, subprocess,
  socket, HTTP, credential, scheduler, strategy, paper, execution, or live
  behavior.

### 19.2 Exact Source Module

- `src/data_layer/point_in_time_market_research/manifest_reference.py`.
- The approved public surface is re-exported from the package `__init__.py`.

### 19.3 Exact Public API

Immutable frozen dataclasses: `DatasetSnapshotReference`, `ManifestEntry`,
`DatasetSnapshotReferenceBuildResult`, `ManifestEntryBuildResult`, and
`ManifestChainValidationResult`.

Public functions:

- `build_dataset_snapshot_reference(input_mapping)` — builds one immutable
  dataset snapshot reference from an explicit mapping or fails closed.
- `build_manifest_entry(input_mapping)` — builds one immutable manifest entry
  from an explicit mapping or fails closed.
- `validate_manifest_chain(entries, *, dataset_references)` — validates a
  complete linear manifest chain over immutable objects.

Public constants: `MANIFEST_REFERENCE_LABEL`, `MANIFEST_REFERENCE_POSTURE`,
`DATASET_REFERENCE_SCHEMA_ID`, `DATASET_REFERENCE_SCHEMA_VERSION`,
`MANIFEST_ENTRY_SCHEMA_ID`, `MANIFEST_ENTRY_SCHEMA_VERSION`,
`DATASET_DERIVATION_MODES`, `MANIFEST_ENTRY_KINDS`, `REFERENCE_STATES`,
`MANIFEST_REASON_CODES`, `MANIFEST_REFERENCE_VALIDATION_STATUSES`, and
`MANIFEST_REFERENCE_ERROR_CODES`. Schema version `1.0.0` defines no warning
codes; every result reports an empty `warning_codes` tuple.

### 19.4 Bounds

- Maximum ID / token / version opaque string: 256 code points.
- Maximum combined ordinary and review-conflict record IDs: 256.
- Maximum manifest entries per chain: 256.
- Maximum supplied dataset references: 256.
- SHA-256 values: exactly 64 lowercase hexadecimal characters.
- Namespaced identities: `record:sha256:`, `datasetref:sha256:`, and
  `manifestentry:sha256:` each followed by 64 lowercase hexadecimal characters.
- Timestamps: UTC `Z` or `+00:00`, at most six fractional digits.
- Booleans never satisfy integer fields; no float is accepted; unknown fields
  are rejected; invalid raw values are never echoed.

### 19.5 Builder Versus Chain-Validator Responsibility

- The two builders validate one object's local structure, closed vocabularies,
  bounds, safety posture, and self-derived identity only. They never reason
  about other entries or references. Each builder recomputes the self identity
  from the canonical preimage (Sections 7 and 9) and compares it; a
  caller-supplied identity is never trusted.
- `validate_manifest_chain` re-derives and revalidates every supplied entry and
  reference through the public builders, then enforces all cross-object
  semantics: the single-manifest hash-linked append chain, subject-reference
  resolution against the registry, the register/supersede/invalidate state
  machine, and human-review binding.

### 19.6 Reference-Registry Requirement

- `validate_manifest_chain` accepts the manifest entries and a supplied registry
  of dataset snapshot references. Every reference is recomputed and revalidated,
  reference identities must be unique, and every manifest subject
  `dataset_snapshot_reference_id` must resolve to a registry reference. Valid
  references that no entry names are permitted.

### 19.7 Input-Order Rule

- Input order is authoritative. The validator never silently sorts. Entries must
  already be in ascending sequence order, sequence numbers must equal `0`
  through `len(entries) - 1`, and each later entry's
  `previous_manifest_entry_id` must equal the exact immediately prior entry's
  `manifest_entry_id`.

### 19.8 Duplicate Registration Rejection

- Each dataset snapshot reference may be registered exactly once. A second
  `REGISTER` of a known subject, a transition targeting a non-effective or
  already-terminal entry, and any reactivation are rejected with
  `MANIFEST_SUPERSEDES_INVALID`.

### 19.9 Human-Review Binding

- For `REGISTER` and `SUPERSEDE`, the entry `human_review_required` must equal
  the referenced `DatasetSnapshotReference.human_review_required`. For
  `INVALIDATE`, `human_review_required` is fixed `true`. The chain result
  `human_review_required` is `true` when any referenced dataset or entry
  requires review.

### 19.10 Fail-Closed Error-Code Precedence

The implementation reports bounded closed codes from `MANIFEST_REFERENCE_ERROR_CODES`
in that locked precedence order. The specific per-field mapping is: a wrong
Python type is `FIELD_TYPE_INVALID`; a malformed value shape (bad SHA-256,
malformed namespaced ID, out-of-range vocabulary, invalid timestamp, oversized
string or count, within-tuple duplicate) is `FIELD_VALUE_INVALID`; a
cross-authority overlap is `REVIEW_CONFLICT_AUTHORITY_FORBIDDEN` and takes
precedence over the generic duplicate rule; a mode-conditional query-field
combination fault is `REFERENCE_MODE_MISMATCH`; a recomputed self identity that
does not match is `ID_DERIVATION_MISMATCH`; and a false or non-boolean
`advisory_only` / `no_execution_authority` is `SAFETY_POSTURE_INVALID`. Invalid
results carry only a fixed status, the ordered closed codes, an empty warning
tuple, null object fields, empty safe tuples, and the fixed advisory /
no-execution booleans.

### 19.11 No Writer, Reader, Or Persistence Authority

- WP160 implements no manifest writer, reader, verifier, file loader, storage
  container, path, atomic append, file locking, crash recovery, migration,
  compaction, Arrow/Parquet, DuckDB/Polars, real collection, feature or label
  construction, replay, paper, or execution behavior. All WP158 deferred items
  remain deferred.

### 19.12 Successor Boundary

- The next separately gated package is WP161 — bounded local persistence design
  and implementation decision for the manifest container, writer, and
  reader/verifier. WP160 grants none of those authorities and does not implement
  WP161.

## 20. WP161 Bounded SQLite Persistence Addendum

WP161 realizes the durable portion of the WP158 contract without changing the
WP160 identity or chain state machine. Its label is
`POINT_IN_TIME_LOCAL_SQLITE_MANIFEST_STORE` and its posture is
`BOUNDED_LOCAL_SQLITE_TRANSACTIONAL_APPEND_AND_VERIFIED_READ`. The only
implementation module is
`src/data_layer/point_in_time_market_research/manifest_store.py`.

### 20.1 Public API

The package exports the constants `MANIFEST_STORE_LABEL`,
`MANIFEST_STORE_POSTURE`, `MANIFEST_STORE_FORMAT_ID`,
`MANIFEST_STORE_SCHEMA_VERSION`, `MANIFEST_STORE_STATUSES`, and
`MANIFEST_STORE_ERROR_CODES`; the frozen dataclasses `ManifestStoreSnapshot`
and `ManifestStoreResult`; and the functions `initialize_manifest_store`,
`append_manifest_store_batch`, and `load_and_verify_manifest_store`.

### 20.2 Exact SQLite Schema And Configuration

The schema format is `point-in-time-manifest-store`, schema version and
`PRAGMA user_version` are exactly `1`, and the database contains exactly these
three application tables:

```sql
CREATE TABLE store_meta (
    singleton INTEGER PRIMARY KEY NOT NULL CHECK (singleton = 1),
    format_id TEXT NOT NULL CHECK (format_id = 'point-in-time-manifest-store'),
    schema_version INTEGER NOT NULL CHECK (schema_version = 1)
)
```

```sql
CREATE TABLE dataset_references (
    dataset_snapshot_reference_id TEXT PRIMARY KEY NOT NULL,
    payload_json TEXT NOT NULL,
    payload_sha256 TEXT NOT NULL
)
```

```sql
CREATE TABLE manifest_entries (
    manifest_entry_id TEXT PRIMARY KEY NOT NULL,
    manifest_id TEXT NOT NULL,
    sequence_number INTEGER NOT NULL CHECK (sequence_number >= 0),
    dataset_snapshot_reference_id TEXT NOT NULL,
    payload_json TEXT NOT NULL,
    payload_sha256 TEXT NOT NULL,
    UNIQUE (manifest_id, sequence_number),
    FOREIGN KEY (dataset_snapshot_reference_id)
        REFERENCES dataset_references(dataset_snapshot_reference_id)
        ON UPDATE RESTRICT
        ON DELETE RESTRICT
)
```

There is exactly one `store_meta` row:
`(1, 'point-in-time-manifest-store', 1)`. There are no application-defined
views, triggers, or indexes. SQLite-managed primary-key and unique-constraint
indexes are verified. Writable connections require `journal_mode=DELETE`,
`synchronous=FULL` (value 2), and `foreign_keys=ON` (value 1). WAL, MEMORY, and
OFF journal modes are forbidden. The Python >=3.11-compatible connection uses
`isolation_level=None`, `timeout=0.0`, and explicit SQL transaction control;
it does not use the Python 3.12 `autocommit` parameter.

### 20.3 Explicit Path And Transaction Rules

The database path is explicit caller input only (`str` or
`os.PathLike[str]`), normalized to an absolute `Path`, and never returned in a
public result. No default, environment-derived, discovered, or global path
exists, and parent directories are never created. Initialization alone may use
SQLite URI `mode=rwc`; append requires an existing regular non-symlink file and
uses `mode=rw`; verified load uses `mode=ro`. Missing targets are never created
by append or load.

Every non-empty append begins with `BEGIN IMMEDIATE`, validates the existing
store while holding the writer transaction, validates the complete prospective
WP160 chain, inserts references before entries using parameter binding, checks
foreign keys, and commits only after every check and insert succeeds. Any
failure rolls back. Lock contention fails immediately as `STORE_BUSY`; there is
no sleep, retry loop, daemon, or multi-writer coordination. Successful
transactions leave no persistent WAL, SHM, or rollback-journal side file.

### 20.4 Canonical Payload, Verified Read, And Idempotency

Every row stores the complete public dataclass content as canonical UTF-8 JSON
produced by `canonical_json_bytes`, plus `sha256_hex` of those exact bytes.
Payloads are limited to 65,536 bytes. Strict decode rejects duplicate keys,
non-finite numbers, non-object top levels, malformed text, and noncanonical
JSON. Every row is re-canonicalized, its digest is recomputed, and its object is
rebuilt through the WP160 public builder. The rebuilt self-ID must equal the row
primary key, and manifest redundant columns must equal the rebuilt fields.

Verified load also requires exact schema/meta/version, `PRAGMA integrity_check`
equal to `ok`, an empty `PRAGMA foreign_key_check`, and a complete successful
`validate_manifest_chain` result whenever entries exist. Read-only load does
not alter the database bytes. Empty and reference-only stores are valid.

Exact-content retries are deterministic no-ops: no historical row is rewritten
and status is `STORE_APPEND_IDEMPOTENT`. A conflicting identity or
manifest-sequence collision rejects the complete batch. The store is bounded to
256 dataset references, 256 manifest entries, one manifest ID in a non-empty
chain, and 65,536 canonical payload bytes per row.

### 20.5 Append-Only, Corruption, And Authority Boundary

The production module uses CREATE, SELECT, and parameterized INSERT for
persisted rows. It exposes no UPDATE or DELETE path, repairs no payload, and
performs no schema migration. Schema drift, configuration drift, SQLite
integrity failure, malformed payloads, semantic tampering, identity mismatch,
invalid input, lock contention, and transaction failure all return bounded
`STORE_REJECTED` results with closed ordered error codes, empty warnings, no
snapshot, empty inserted/idempotent ID tuples, and fixed advisory/no-execution
flags. No path, raw payload, SQL, exception, traceback, or OS detail is echoed.

WP161 authorizes no migration, compaction, VACUUM policy, backup/export,
signing/attestation, Arrow/Parquet, DuckDB/Polars, analytics, market-data
collection, feature or label construction, backtest/replay engine, strategy,
paper trading, account/portfolio/risk/reconciliation, order, execution,
credential, network, scheduler, bot-loop, or live-trading behavior. Adapters
from WP156/WP157 outputs, real/public dataset population, and every later layer
remain separately gated successor work.

No WAL is enabled, no network behavior is added, no live-trading behavior is
authorized, and no successor capability is implemented by this package.
