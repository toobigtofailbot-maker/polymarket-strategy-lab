1. OBJECTIVE

Replace universal heavy certification with three mechanically routed governance tracks while
preserving strict controls where credentials, signing, execution, live authority, or Risk 4 are
present. FAST covers offline/local research, analytics, UI, docs, tests, and ordinary tooling.
RUNTIME covers explicitly authorized network/runtime/scheduler/Hermes/paper work without
credential, execution, or live authority. PROTECTED retains the current immutable independent
draftability-certificate workflow.

Normal work becomes concise prompt/spec, deterministic readiness, implementation, targeted
validation, one stable-candidate broad validation, hosted CI, and independent Side review.
Protected work retains the strict immutable package, independent certificate, strongest
validation, and Side review. This WP changes governance/tooling only and adds no bot runtime or
trading capability.

7. GOVERNANCE TRACK ROUTING

Every future WP prompt must state exactly one `Governance track expected: FAST`, `RUNTIME`, or
`PROTECTED` line. Readiness independently derives the minimum allowed track from existing spec
risk/authority fields and rejects a weaker prompt track. A package may choose a stricter track.

PROTECTED minimum if risk_level is 4 or credentials, execution, or live is true.
RUNTIME minimum if not PROTECTED and risk_level is 3 or network, scheduler, hermes_runtime, or
paper is true.
FAST minimum otherwise when risk_level is at most 2 and credentials, execution, live, paper,
scheduler, and hermes_runtime are false.

8. PRE-IMPLEMENTATION READINESS BY TRACK

FAST and RUNTIME require deterministic prompt/spec/schema/semantic/readiness checks, completed
compatibility analysis, declared authority/scope, no unresolved decisions, and a clean current
predecessor. RUNTIME also requires explicit runtime authority and the stronger class-specific
negative/security plan. Neither requires an independent pre-implementation LLM certificate.

PROTECTED retains the exact prompt/spec/certificate topology, certificate hash/semantic checks,
and all current PROTECTED-strength behavior. Existing historical certified packages remain valid.

9. DRAFTABILITY_PASS SEMANTICS

For FAST/RUNTIME, DRAFTABILITY_PASS means deterministic prompt/spec/readiness checks completed
with no open decisions; it does not claim independent LLM review. For PROTECTED it retains the
independent certificate-bound meaning. Readiness output and docs must name the establishing
track and must never call FAST/RUNTIME readiness an independent certificate.

10. SCOPE CORRECTION / RECERTIFICATION

FAST/RUNTIME use bounded discovery, then allow one batched same-capability scope correction
inside authority and size budget followed by deterministic spec/readiness rechecks only.
PROTECTED retains semantic-change invalidation and independent recertification.

11. VALIDATION BY TRACK

FAST editing uses focused/adjacent/cheap checks. Its stable candidate uses readiness --check-diff,
actual-surface security checks, exact-head hosted CI, an authoritative broad/full suite locally or
by equivalent exact-head CI, and mandatory Side review. No internal final LLM reviewer is required
unless the WP asks for one.

RUNTIME editing adds directly affected integration and runtime/network boundary checks. Its stable
candidate uses one combined independent implementation reviewer, one authoritative full suite
local or exact-head hosted, exact-head CI, and Side review.

PROTECTED retains independent pre-implementation certification, boundary/security tests, full
security/credential checks, full suite, exact-head CI, required final independent review, Side
review, and explicit user authorization for live-capital transitions. No track converts a failed
required check into Ready YES.
