  - `live_orch_state_root` differs from the case state root;
  - the signer or wallet differs from the case;
  - `approved_menu` differs from the case menu after canonical JSON;
  - the side or attempt count differs;
  - the envelope differs from the native frozen LIVE-ORCH constants (100/5/30/70).
- STAGE_A_LEDGER_UNINITIALIZED: that native ledger is missing, has no events, or fails the native GatewayStore load and replay validation that LiveOrchestrator uses. The read opens no store in create mode and writes nothing; the composer never creates, recreates or clears the ledger.
- STAGE_A_CONSUMED: the ledger exists and is replay-valid, but its head differs from `ledger_head_at_approval`.

Single use (A). One Stage A allows at most one economic admission or CREATE attempt:
- Run lock. `run` acquires the native O_EXCL `WalletSessionLock` class (gate_b.py:212-250) with directory `<live_orch_state_root>/live_canary`. This is a different file from the native Gate-B wallet lock under `<state_root>/live_orch`, which LIVE-ORCH never stops taking itself. The run holds it from step C1 until `.canary` returns or the run stops. A held lock gives STAGE_A_RUN_LOCKED with zero OAuth and zero canary. The lock is an exclusion file holding only the public wallet. It is not an economic store, and no native code ever acquires it, so it cannot deadlock the native wallet lock.
- Last boundary. Under that lock, immediately before `.canary`, the composer re-reads the window and requires the ledger to exist, replay cleanly and carry exactly the approved head (otherwise STAGE_A_LEDGER_UNINITIALIZED or STAGE_A_CONSUMED). Any admission appends native ledger events, so a later run sees a changed head and stops with STAGE_A_CONSUMED.
- Concurrent runs. Two runs with the same Stage A serialize on the lock. The second one sees the changed head.
- Different state root. A run pointed at any other root fails STAGE_A_SCOPE_MISMATCH.
- Same path, ledger removed or recreated. A deleted ledger is missing, so STAGE_A_LEDGER_UNINITIALIZED. A recreated ledger has a different head, because its INITIALIZED event hash covers a new event ID and time (gateway.py:2539-2550; store.py chain hash), so STAGE_A_CONSUMED. Either way it stops before OAuth in `check`, or at the last boundary before `.canary`. Native canary would otherwise create a missing ledger at session open (live_orch.py:990-994), so the last-boundary existence check is mandatory.
- Crash after native admission. The episode is already durable in the native ledger, so the head has changed. A stale run lock fails closed (STAGE_A_RUN_LOCKED) until the operator runs native `live_orch reconcile`, which takes no composer lock and stays fully available, and removes the stale lock by hand.
- Accepted cost. Any native ledger event after approval, including a reconcile, also consumes Stage A. Karl must then issue a new Stage A.
- Residual, declared and not hidden: privileged rollback. Code cannot detect someone with host privileges deliberately restoring an old, otherwise valid copy of the ledger file that still carries the approved non-empty head. That is a trusted-host integrity assumption, the same one native PERMIT_ALREADY_CONSUMED relies on. Hashes alone do not prevent it.
  - Native account truth still blocks a remaining resting order or position (ACCOUNT_UNKNOWN_OPEN_ORDER, ACCOUNT_POSITION_UNKNOWN). It does not block a cancelled, unfilled order.
  - It is excluded by approved host access controls and backup handling (runbook, section 7(i)), not by code.
  - The native `live_orch canary` CLI does not take the run lock. It is not an authorized route for this canary (item 13).

Economics (B). Stage A approves no ceiling tighter than the frozen USD 5 single-order worst-case cap. That cap is enforced natively at final admission: `check_admission_risk` raises SINGLE_ORDER_LIMIT_EXCEEDED when principal + canary-time fee reserve > 5 (live_orch.py:837-842), and this runs after canary's own fresh venue snapshot and fee recomputation. The bridge-time principal and fee shown in the summary are informational only. No composer-side ceiling is claimed, and live_orch.py gains no ceiling parameter.

Pre-canary checks, after bridge PASS and again under the run lock after Stage B:
- STAGE_A_WINDOW_INVALID: the window is rechecked against the clock.
- STAGE_A_LEDGER_UNINITIALIZED or STAGE_A_CONSUMED: the ledger's existence, replay validity and exact head are rechecked.
- STAGE_A_SCOPE_MISMATCH: the intent's strategy version, condition and token are not in `approved_menu`, or the side is not BUY.
- PERMIT_INTENT_MISMATCH: the permit and intent are not the native exact pair. Native LIVE-ORCH validation still runs as well.

Authorship (C).
- Code cannot detect a well-formed, fully conformant artifact that Karl never approved: the digest comes from the same operator case.
- Owner approval is established only outside code, by Karl's authentic post-merge activation record naming the full Stage A SHA-256 (section 7(h)). Without that record there is NO LIVE RUN.
- The full digest display and the typed Stage A suffix (step C9) are Karl's correlation against his own record, not authentication.
- Receipts label the result `stage_a_binding: MACHINE_CONFORMANCE_ONLY_OWNER_APPROVAL_EXTERNAL` and never claim owner authentication.
- The artifact holds no secret, and its path is never echoed.

# 5. SEMANTIC/FALSE-CLAIM SAFETY
- The canary is execution-mechanics validation only. It is not edge, profitability or strategy qualification. Native policy, Gate C and Hermes abstention (for example PAPER, ADAPT, or a stale or missing assessment) stay binding even when they prevent the trade, and the composer never overrides or works around them.
- ONE_CREATE_ATTEMPTED is not a fill, a profit or strategy validation. Passive post-only orders may rest unfilled and are cancelled natively after the at most 60 s observation.
- A valid canonical assessment's provider and model labels are not proof of authenticated inference. The OAuth witness proves only where the choice bytes came from.
- The composer handles no secret. The signer key is entered only into the native Gate-B no-echo prompt inside canary. The OAuth credential directory is passed only to the native transport. Neither is printed, logged, copied or persisted.
- No proxy, VPN, alternate host or geographic workaround is added or suggested. A blocked geoblock is terminal for that host and operator.
- No scheduler, daemon, background thread, loop over markets, auto-retry, SELL, size scaling or envelope change.
