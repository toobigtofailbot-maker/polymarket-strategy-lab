12A. COMPLETE META-SCHEMA, BOUNDS, SET RULES, AND GENERIC DERIVATION
----------------------------------------------------------------------

`WP_SPEC_STANDARD.md` and the guard must implement the following rules exactly.
The executor may not invent another nested schema, vocabulary, bound, ordering
rule, or derivation algorithm.

A. Input bounds and JSON parsing

- Maximum WP prompt bytes: 1,048,576.
- Maximum specification bytes: 1,048,576.
- Maximum certificate bytes: 262,144.
- JSON must be UTF-8 without a BOM.
- Duplicate JSON object keys reject as `JSON_PARSE_INVALID`.
- `NaN`, `Infinity`, and `-Infinity` reject as `JSON_PARSE_INVALID`.
- Numeric literals that decode to a non-finite value, including exponent
  overflow such as `1e9999`, reject as `JSON_PARSE_INVALID`.
- Maximum JSON nesting depth after parse: 32, where the root is depth 1.
- Maximum string length: 16,384 Unicode code points unless a smaller field
  bound below applies.
- Maximum array length: 1,024 unless a smaller field bound below applies.
- JSON booleans never satisfy integer or number types.

B. Exact object keys and field types

Every object below rejects unknown keys. `string[a,b]` means a string whose
Unicode-code-point length is in the inclusive range. `token` means
`^[A-Z][A-Z0-9_]{0,127}$`. `sha40` means exactly 40 lowercase hexadecimal
characters. `sha256` means exactly 64 lowercase hexadecimal characters.

`identity` has exactly:

- `wp_id`: string matching `^WP[1-9][0-9]*(?:[A-Z])?$`;
- `title`: string[1,200];
- `repository`: string[3,200] matching one `owner/name` pair;
- `package_class`: token;
- `package_size_class`: one of `S`, `M`, `L`, `XL`;
- `risk_level`: integer 0..4;
- `base_branch`: repository-relative ref token string[1,200], with no
  whitespace, control character, `..`, `~`, `^`, `:`, `?`, `*`, `[`, or
  backslash;
- `required_predecessor`: object with exactly `pr_number` (positive integer),
  `head_sha` (sha40), and `merge_sha` (sha40);
- `suggested_branch`: string[1,200] satisfying the same ref restrictions;
- `objective`: string[1,2000];
- `capital_at_risk_usd`: finite JSON number >= 0;
- `xl_explicit_authorization`: boolean;
- `xl_authorization_basis`: null unless size is XL; for XL it is
  string[1,1000] and `xl_explicit_authorization` is true.

`scope` has exactly:

- `required_changed_files`, `allowed_changed_files`,
  `historical_compatibility_edits`: arrays of normalized paths;
- `forbidden_prefixes`: array of normalized directory prefixes ending `/`;
- `max_changed_files`: positive integer;
- `exact_scope_required`: boolean;
- `rollback_surface`: string[1,2000];
- `mode_boundaries`: array of objects with exactly `boundary` (lowercase token
  matching `^[a-z][a-z0-9_]{0,127}$`) and `crossed` (boolean).

Normalized paths are non-empty repository-relative forward-slash paths. They
reject absolute paths, drive letters, empty segments, `.`/`..` segments,
backslashes, NUL/control characters, a trailing slash, and leading `./`.
Path comparison is case-sensitive. Lists are order-preserving but duplicate
paths reject. Required and allowed lists contain at most 35 paths; forbidden
prefixes at most 64. Historical compatibility paths must be a subset of allowed
paths. Mode-boundary names are unique.

Package budgets are S<=5, M<=10, L<=20. For S/M/L,
`max_changed_files` must not exceed the budget. For XL, explicit authorization
and basis are mandatory. `len(required_changed_files)` must be <=
`max_changed_files`; required must be a subset of allowed.

`authority` has exactly these sixteen boolean fields:
`workflow_governance`, `local_offline_tooling`,
`canonical_evidence_policy`, `docs`, `tests`, `source_runtime`,
`workflow_files`, `dependencies`, `network`, `credentials`, `scheduler`,
`hermes_runtime`, `strategy`, `paper`, `execution`, `live`.

Every applicability object has exactly `applicable`, `reason`, `items`.
`applicable` is boolean; `reason` is string[1,1000]. True requires 1..1024
items. False requires zero items. The reason is always required; it explains
either applicability or non-applicability.

`api_matrix.items[]` has exactly:
`surface` string[1,300], `before` string[1,1000], `after` string[1,1000],
`change_authorized` boolean, `compatibility_requirement` string[1,1000], and
`authority` token. Surfaces are unique.

`semantic_fields.items[]` has exactly:
`path`, `source`, `type`, `required_rule`, `mutable`, `identity_role`,
`exclusion_reason`, `validation_rule`, `failure_category`, `safe_output`,
`derivation_rule_id`. `path` is a unique dot path whose segments match
`^[A-Za-z_][A-Za-z0-9_]{0,127}$`; `source` is one of
`CALLER`, `CONSTANT`, `DERIVED`; `type` is string[1,128];
`required_rule`, `validation_rule`, and `safe_output` are string[1,1000];
`mutable` is boolean; `identity_role` is `COMMITTED`, `EXCLUDED`, or `NONE`;
`failure_category` must name a category in `failure_precedence`;
`exclusion_reason` is string[1,1000] exactly when identity role is EXCLUDED and
null otherwise; `derivation_rule_id` is a rule ID or null. EXCLUDED may not be
mutable. DERIVED+COMMITTED requires an existing derivation. DERIVED+NONE may
use null only when `validation_rule` is non-empty.

`identity_derivations.items[]` has exactly:
`rule_id`, `target_path`, `algorithm`, `source_paths`, `excluded_paths`,
`prefix`, `canonicalization`. Rule IDs and target paths are unique. Rule IDs
match `^[a-z][a-z0-9_]{0,127}$`. Target/source/excluded paths are dot paths;
within each list paths are unique and source/excluded sets are disjoint.
`algorithm` is `SHA256_RAW_BYTES` or `SHA256_CANONICAL_JSON`; `prefix` is
string[0,128].

For `SHA256_RAW_BYTES`: there is exactly one source path; it is exactly one of
`$external.wp_file_bytes` or `$external.wp_spec_file_bytes`; excluded paths are
empty; prefix is empty; canonicalization is null; the target is
`prefix + sha256(exact_source_bytes).hexdigest()`.

For `SHA256_CANONICAL_JSON`: the target, every source path, and every excluded
path are dot paths relative to the same example `input`. Canonicalization has
exactly:

```json
{
  "sort_keys": true,
  "separators": [",", ":"],
  "ensure_ascii": false,
  "allow_nan": false,
  "encoding": "utf-8",
  "preserve_explicit_nulls": true,
  "preserve_array_order": true
}
```

Every source and excluded path must exist. Source paths may not equal or be an
ancestor/descendant of another source path. Each excluded path must be a strict
descendant of exactly one source path; it may not equal a source path. Resolve
each source value, deep-copy it, and remove the excluded descendant paths from
that copy. Excluded paths may traverse JSON objects only; array-index path
segments are not supported. If `target_path` is equal to or below a source
path, it must be listed in `excluded_paths`; otherwise the derivation is
self-referential and rejects as `IDENTITY_DERIVATION_INVALID`.

The preimage is a JSON object whose keys are the full source-path strings in
declared order and whose values are the corresponding projected source copies.
Object-key sorting during serialization makes source declaration order
non-identity-bearing; array order within values remains identity-bearing.
Serialize with the exact canonicalization object above. Resolve the expected
target at `target_path` in the original example input. Its required value is
`prefix + sha256(canonical_bytes).hexdigest()`. Missing paths, invalid
exclusions, a non-string target, or a mismatch reject as
`EXAMPLE_TRUTH_INVALID`, except the self-reference rule above.

Focused tests for the generic algorithm must use an applicable canonical-JSON
example and prove: every included scalar-leaf mutation changes the digest; an
excluded scalar-leaf mutation does not change it; array reordering changes it;
object insertion-order changes do not; prefix changes alter only the prefixed
result; and the target is resolved relative to `input`, never relative to the
wrapper or the specification root.

`state_transitions.items[]` has exactly:
`from_state`, `to_state`, `condition`, `failure_category`. States are tokens;
condition is string[1,2000]; category must exist in precedence. Transition pairs
are unique; self-transitions reject.

`failure_precedence.items[]` has exactly:
`condition_id`, `category`, `priority`. Condition IDs match the derivation-rule
ID grammar and are unique. Categories are tokens and unique. Priorities are
unique positive integers. For schema 1.0.0 the items must be exactly the fifteen
conditions/categories/priorities in the WP159 spec and in the order shown there.

`examples.items[]` has exactly:
`example_id`, `expected_valid`, `expected_error_codes`,
`intended_fault_count`, `derivation_rule_ids`, `input`.
Example IDs are unique string[1,200]; booleans and fault count have their normal
types; error codes are unique precedence categories in canonical precedence
order; derivation IDs are unique and existing; input is a JSON object. A valid
example has no errors, zero faults, and every listed canonical derivation
recomputes. An invalid example has exactly one fault and one or more expected
errors. The guard validates the wrapper and derivations; domain-specific example
validity is asserted by the WP's focused tests and must equal the wrapper claim.

`evidence_plan.items[]` has exactly:
`requirement_id`, `source`, `test`, `command`, `expected_result`.
Requirement IDs are unique and match `^R[0-9]{2,4}$`; all other fields are
string[1,4000]. Commands must not contain NUL or a newline.

D. Set/batch ordering

All arrays preserve declared order in parsed/validated data. Duplicate identity
keys reject. Guard errors are collected without set iteration. Errors sort by:
failure priority, then canonical schema field path, then error code. Unknown
object keys produce one `UNKNOWN_FIELD` error at the known parent path; the
untrusted key is never echoed. Array-item errors use a numeric index in the
field path. This ordering applies identically to text and JSON formats.

E. Certificate schema

The certificate is a separate JSON document and is never a field of the spec.
It has exactly the thirteen keys listed in Section 12. Strings use the exact
constants already listed. `wp_text_sha256` and `wp_spec_sha256` are sha256;
`reviewed_base_merge_sha` is sha40; `covered_lenses` has exactly twelve objects,
each with exactly `lens` and `result`, in canonical order, each result PASS.
`unresolved_decisions` is exactly an empty array. No certificate hash, bytes, or
content is included in the specification. Therefore the only hash edges are
`certificate -> WP bytes` and `certificate -> spec bytes`; no cycle exists.

`wp_id` uses the WP-ID grammar and must equal `spec.identity.wp_id`.
`reviewed_repository` is string[3,200], uses the same exact repository grammar
as `spec.identity.repository`, and must equal it.
`reviewed_base_merge_sha` must equal
`spec.identity.required_predecessor.merge_sha`. A syntactically valid mismatch
in any of these three cross-document identity fields is
`DRAFTABILITY_INCOMPLETE`. A malformed field is `FIELD_TYPE_INVALID` or
`FIELD_VALUE_INVALID` as applicable. A syntactically valid but unequal raw-byte
digest is `CERTIFICATE_HASH_MISMATCH`. Certificate constant, lens, result,
attestation, unresolved-decision, or implementability defects are
`DRAFTABILITY_INCOMPLETE`.

The repository grammar is exactly
`^[A-Za-z0-9](?:[A-Za-z0-9._-]{0,99})/[A-Za-z0-9](?:[A-Za-z0-9._-]{0,99})$`.
This same expression applies to `identity.repository`; no executor-selected
repository regex is permitted.

F. Diagnostic field paths, cardinality, and phase gating

Diagnostic `field_path` values are trusted schema locations, never
caller-supplied field values. Root labels are exactly `cli`, `files.wp`,
`files.spec`, `files.certificate`, `spec`, and `certificate`. Nested object
locations use dots. Array locations use zero-based brackets, for example
`spec.api_matrix.items[0].surface`.

- a missing field names the trusted expected field location;
- an invalid present field names that field location;
- an unknown-key error names only the known parent object;
- each object emits at most one `UNKNOWN_FIELD` error regardless of how many
  unknown keys it contains;
- duplicate JSON keys emit one `JSON_PARSE_INVALID` error at `spec` or
  `certificate`;
- duplicate array identities emit one error for each second-or-later
  occurrence at that occurrence's trusted identity-field location;
- identical `(code, field_path, message)` errors deduplicate by first
  occurrence without set iteration.

The guard uses the following closed phase gate:

1. CLI usage validation. A usage defect returns `USAGE_ERROR`, one
   `FIELD_VALUE_INVALID` error at `cli`, empty `checked_sections`, and exit 2.
2. `files`. Attempt bounded regular-file reads for all three roles. Any missing,
   unreadable, non-regular, or over-limit role emits `FILE_READ_ERROR` at its
   fixed `files.*` path, returns `USAGE_ERROR`, stops before JSON parsing, and
   exits 2.
3. `spec_json`. Strictly decode/parse the spec. On failure, return `FAIL`,
   stop all later sections, and exit 1.
4. `spec_schema`. Check exact keys, types, bounds, constants, and field-local
   grammar. Any error through `FIELD_VALUE_INVALID` stops later sections.
5. `spec_semantics`. Check applicability, uniqueness, scope/budgets,
   authority, cross-references, derivations, transitions, fixed precedence,
   examples, evidence, and successor rules. Any semantic error stops before
   certificate checks.
6. `certificate_json`. Strictly decode/parse the certificate. Parse failure
   stops later certificate sections.
7. `certificate_schema`. Check exact keys, types, bounds, and field-local
   grammar. Any schema error stops later certificate sections.
8. `certificate_hashes`. Compare the two certificate digests with the already
   computed exact raw-byte digests.
9. `certificate_draftability`. Check cross-document identity, constants,
   attestation, exact lens order/results, empty unresolved decisions, and
   implementability PASS. This phase runs even if the preceding hash comparison
   found mismatches, so both bounded categories may be reported.

`checked_sections` is the exact prefix of the canonical section list whose
phases started. The fixed built-in precedence table, not an invalid
document-supplied table, sorts diagnostics. Within a category, sort by the
diagnostic path grammar above and then code; stable first occurrence breaks a
fully equal tie.

`validate_spec_document` applies `spec_schema` and `spec_semantics` only. It
accepts JSON-compatible built-in values, detects cycles, non-finite numbers,
and excessive depth, and returns sanitized errors for caller-controlled invalid
content. Expected `TypeError`, `ValueError`, `UnicodeError`, `OSError`, and
`RecursionError` conditions are converted to closed errors; exception text is
never returned. A defect in the guard's own internal constants is a programmer
error and may raise.
