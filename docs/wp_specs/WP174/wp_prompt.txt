REPO-OWNED GAP LAYER

Implement a narrow src/execution_gateway/gateway.py wrapper around the selected SDK. It owns the
A0 DISABLED, A1 READ_ONLY, and A2 SHADOW authority gates; WP173 intent/authorization binding;
canonical Decimal normalization; LIMIT-only instruction allowlisting; secret reference loading and
redaction; transport classification; heartbeat request/ack safety; user-stream gap state; dynamic
access/venue-state enforcement; and sanitized cockpit projection. It may contain a Gate-B-only
mutation transport entry point, but that entry point must be unreachable in all WP174 ordinary
configuration and tests.

Implement src/execution_gateway/store.py as the dedicated SQLite journal and recovery boundary for
authority state, request/order identity, mutation attempts/outcomes, reconciliation state,
heartbeat/user-stream/access state, disable state, and a tamper-evident audit chain. Startup,
restart, ambiguity, or divergence must fail closed.

The SDK has no public heartbeat method and does not provide the complete repo persistence,
idempotency, ambiguity, and authority model. The narrow gap layer may call only the documented
heartbeat endpoint using the same server-side L2 credential boundary; it must not recreate the SDK
signing stack or become a general direct CLOB client.

REJECTED ALTERNATIVES

- py-clob-client-v2==1.1.0 is rejected as primary. It is compatible with the repo pin set, but
  current evidence includes signer/deposit-wallet binding issues, float-precision risks, a global
  transport, response-body/URL error logging, hidden response headers, and a POST retry option with
  unsafe ambiguity implications. Released v1.1.0 provenance, not mutable main, was evaluated.
- nautilus_trader==1.231.0[polymarket] is rejected as primary. The repo already pins the base
  package and tag commit 27a8e54e7ac3c57d6cbf8891f0283dfbaee97317 was evaluated, but the extra
  installs py-clob-client-v2 and introduces a second execution/reconciliation state model broader
  than this gateway. It also inherits the lower SDK risks and documented venue edge cases.
- A custom full direct HTTP/signing client is rejected because it would duplicate audited wallet,
  authentication, and EIP-712 functionality and materially enlarge the protected surface.
- Unsupported dependency suppression such as --no-deps is forbidden as a production design.

Known selected-SDK gaps frozen for implementation: no public heartbeat API; no repo-owned durable
idempotency/recovery model; transport metadata/hook coverage must be verified and safely wrapped;
current market BUY rounding issue makes market-order creation unsafe; partial settlement and
transport-injection issues remain upstream concerns. Any gap that cannot be closed inside the exact
scope is a hard stop.

4. CAPABILITY, AUTHORITY, AND SECRET CONTRACT
===============================================================================

Capabilities are distinct from authority:
- C1 authenticated reads;
- C2 normalize/build an exact would-submit order;
- C3 fixture signing, and real signing only after Gate B;
- C4 mutation transport present but locked behind Gate B;
- C5 authoritative account reconciliation.

WP174 runtime authority states are closed:
- A0 DISABLED: no authenticated mutation and no real-secret signing exercise.
- A1 READ_ONLY: separately authorized authenticated reads only; no create/cancel/signing mutation.
- A2 SHADOW: consume authorized intents, normalize/build, run all deterministic gates, persist
  would-submit artifacts, and optionally use fake fixture signing; no venue mutation.
- A3 RESTRICTED_LIVE does not exist in WP174 and cannot be parsed, configured, restored, or
  reached. WP175 must add it under Gate C.

Secret references are accepted only through one explicit server-side loader boundary. Protected
material includes signer private keys, API secret/passphrase, and future builder/relayer secrets.
No values may enter Git, fixtures, URLs, logs, exceptions, SQLite, audit output, API responses,
browser state, screenshots, generated evidence, or Hermes context. Loading fails closed. Public
address/funder/signature-type metadata may be emitted only after validation and sanitization.

No config, environment variable, cockpit route, credential presence, persisted state, SDK default,
or agent/Hermes input may elevate authority. The store persists DISABLED/kill state across restart.

===============================================================================
5. FROZEN LIMIT-ORDER SURFACE
===============================================================================

Initial mutation-capable construction is LIMIT only:
- one deterministic LIMIT order per logical execution intent;
- GTC and GTD only when current venue constraints confirm support;
- post-only only when the current venue contract confirms it for the exact instruction;
- exact Decimal price and quantity normalization using current authoritative tick/min-size data;
- explicit worst acceptable price and deterministic upstream WP173 authorization identity;
- exact signer, funder/maker, wallet/signature type, chain/domain, market/condition, token,
  NegRisk/exchange, nonce/timestamp, and signed-order-hash binding.

Explicitly unsupported in WP174:
- MARKET, FAK, FOK, fill-or-kill, immediate-or-cancel, stop, trigger, trailing, or conditional orders;
- batch order creation;
- reduce-only flags or inferred close-only exposure reduction;
- broad wallet transfers, approvals, portfolio allocation, strategy sizing, or capital deployment;
- mutation created from cockpit, browser, Hermes, or any unbound request;
- blind retry of create or cancel after a possibly transmitted request.

Cancel capability is limited to one order and bounded cancel-many/cancel-market/cancel-all control
paths justified by reconciliation or kill handling. These paths remain Gate-B prohibited. Query
coverage is order by venue ID, open orders, recent relevant fills/trades, required balances/
positions, and current access/account/venue mode. Cancellation may remain available while new
exposure is disabled only after Gate B and only when venue state permits.

===============================================================================
6. IDENTITY, MUTATION, RECONCILIATION, AND RECOVERY
===============================================================================

Canonical order identity is SHA-256 over canonical JSON containing the execution-intent ID,
WP173 deterministic authorization/risk identity, strategy/session, chain/domain/protocol version,
signer/funder/wallet/signature type, condition/market/token, side, LIMIT type, TIF, canonical Decimal
price/quantity, tick size, minimum size, NegRisk/exchange, post-only flag, nonce and signing-time
fields. Transport results and venue order IDs are excluded from this pre-mutation identity.

Mutation-attempt identity is SHA-256 over canonical JSON containing the order identity, closed
operation token, monotonic attempt sequence, prior reconciliation state, and exact non-secret
request digest. One logical intent cannot map to a second economically equivalent order.

Closed outcome states include DEFINITIVE_ACCEPTED, DEFINITIVE_REJECTED, AMBIGUOUS, and
RECONCILIATION_REQUIRED. Timeouts/disconnects/crashes/425/429/5xx/malformed responses/adapter
omissions/local post-transmit failures are ambiguous unless authoritative evidence proves otherwise.
Ambiguous create or cancel freezes further mutation for the logical identity and reconciles orders,
trades, balances/positions, and signed/order identity before any conclusion. Unknown stays blocked.

Authoritative reconciliation is mandatory at startup, restart with possible resting orders,
user-stream reconnect or gap, ambiguity, unexpected venue/local disagreement, and explicit operator
request. The authenticated stream accelerates awareness but is not canonical account truth.
Unexpected/foreign/unreconciled venue state blocks new exposure-capable mutation.

Heartbeat is an order-safety protocol. One process owns heartbeat credentials and order-lifetime
expectations. The gateway persists heartbeat identity/ack/failure, enters unsafe disconnected state
on missed or malformed acknowledgement, and requires reconciliation before recovery. Rate handling
uses response headers and Retry-After where exposed, bounded backoff, and separate read-vs-mutation
policies; mutation retries never duplicate economic exposure.

Geoblock, close-only, cancel-only, matching-engine/restart, post-only, and eligibility state are
queried dynamically and fail closed when unknown or blocked. Geographic restrictions are never
bypassed. WP174 does not infer safe reduction from a nonexistent reduce-only field.
