5. DETERMINISM / IDENTITY & EQUAL-TIMESTAMP ORDERING (FROZEN POLICY)
===============================================================================

Project canonical identity does NOT become Nautilus file/catalog identity. Define a
repo-controlled NautilusReplayReceipt identity from: exact source dataset id; exact
frozen conversion-policy version; exact nautilus version; deterministic instrument
semantic identity; ordered converted-event semantic digests; and replay
configuration limited to deterministic offline-replay settings. Exclude absolute
paths, temp dirs, non-semantic Parquet physical bytes, wall-clock time, environment
identifiers, CI run ids, and hostnames. Mutation-sensitivity tests are required.

FROZEN EVENT_KIND_RANK (deterministic tie-break only; NOT a venue-causality claim;
changing this mapping changes the conversion-policy identity/version):
  book            = 0
  price_change    = 1
  last_trade_price= 2
  tick_size_change= 3
This mapping is fixed in the prompt/spec. It must never be derived from alphabetical,
enum-declaration, or any runtime-dependent ordering.

CANONICAL SEMANTIC SOURCE ORDERING (frozen — total and physical-order-independent):
The converted event stream is ordered by a canonical semantic ordering derived only
from validated row content, never from physical/enumeration/query order:
A. For every validated pmxt v2 source row, derive canonical semantic row bytes from
   the validated row content using an explicitly deterministic serialization.
B. Derive a stable canonical_row_digest from those canonical semantic bytes.
C. Construct the canonical source multiset INDEPENDENTLY of: filesystem enumeration
   order; Parquet file enumeration order; Parquet physical row position; DuckDB/
   Polars/query return order; Python stable-sort input order; and temporary/output
   paths.
D. Group rows whose canonical semantic bytes are exactly identical.
E. Sort the distinct canonical row groups deterministically by the total key
   (ts_event, ts_init, event_kind_rank, canonical_row_digest, canonical_row_bytes),
   using canonical_row_bytes as the final collision-safe semantic tie-break rather
   than relying on the digest alone.
F. For an exactly byte-identical duplicate group with multiplicity N, deterministically
   expand it with duplicate ordinal 0, 1, ..., N-1. The duplicate ordinal is derived
   from multiplicity in the canonical multiset, NOT from original physical/source order.
   Identical source rows are NEVER silently deduplicated; multiplicity is preserved
   deterministically.
G. source_row_index is the final zero-based position in this canonical expanded source
   sequence. A monotonic sequence equal to source_row_index is assigned from the
   canonical order.

The engine-facing per-event order key remains (ts_event, ts_init, event_kind_rank,
source_row_index); add_data is used with its default stable ts_init sort, and because
source_row_index already encodes the full canonical order, equal-ts_init events
dispatch in the canonical order. source_row_index MUST NOT be derived from arbitrary
filesystem enumeration, arbitrary file-list order, nondeterministic database/query
ordering, Parquet physical row number, Parquet rewritten physical row position,
caller input order, or Python stable-sort preservation of an arbitrary original order.

REPLAY IDENTITY CONSEQUENCES:
The same validated semantic multiset must produce the same ordered event stream and
the same replay digest even if source files are enumerated differently, Parquet files
are physically rewritten, identical rows occur more than once, or query engines return
equal-key rows in a different physical order. The replay digest is therefore SENSITIVE
to duplicate multiplicity (multiplicity 2 vs 3 differs) but INSENSITIVE to arbitrary
physical ordering. Raw source/query/physical row index is never part of logical replay
identity. If the exact Nautilus or WP167 data model makes this ordering impossible,
STOP rather than introducing another physical-order dependency.

6. TICK-SIZE-CHANGE POLICY (FROZEN — PREFERRED MODEL SELECTED)
===============================================================================

The prototype proved (against 1.231.0) that a single BinaryOption instrument at the
finest valid price increment of the stream represents every historical price
losslessly (all stream prices are exact integer multiples of the finest tick within
FIXED_PRECISION == 9), and that a coarse-tick instrument would fail to represent a
finer historical price. Therefore the PREFERRED model is adopted:

- Preserve ONE stable Polymarket instrument identity per market/outcome token.
- Use the finest valid price increment required by the historical stream.
- Commit the exact tick-size regime transition schedule (old_tick_size,
  new_tick_size, transition timestamps) in repo-controlled conversion/replay
  metadata and in the replay receipt.
- Instrument identity does NOT change merely because venue tick size changed.
- WP168 makes NO order-validity, execution, or fill claim about tick regimes.
- A future implementation test must prove that every validated historical price in the
  stream is an exact integer multiple of the selected finest price increment; the
  conversion fails closed (NAUTILUS_EVENT_CONVERSION_INVALID) for any dataset where
  that does not hold.

FALLBACK (only if a future exact-version reverification makes the single-instrument
model semantically invalid or rejects historical events): deterministic replay
segmentation by tick-size regime, proving deterministic segment boundaries and
segment ids, a stable relationship back to the same market/outcome token, no event
loss or duplication across boundaries, a receipt that commits the regime sequence,
and segmentation never misrepresented as multiple economic markets. Segmentation is
NOT chosen merely because it is easier. On this frozen pin the preferred model is
selected and segmentation is not required.
